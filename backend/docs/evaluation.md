# Evaluation report

All numbers were **measured on 2026-10-29** by running the real system
(Docker Compose stack: API, workers, PostgreSQL, Redis, UploadThing, Mistral)
and scoring the API's output against labels. Raw results:
[`evaluation/results/`](../evaluation/results). Reproduce with
`make evaluate` and `make benchmark`.

## Method

**Labeled dataset** ([`evaluation/dataset/`](../evaluation/dataset), 37
files, labels in `labels.json`, generated by `evaluation/build_dataset.py`):

| Kind | Files | Notes |
|---|---:|---|
| Native PDF | 16 | 2 credit notes, 2 with an injected total error, varied currencies, date styles (ISO, d/m/y, "24 Apr 2026") and number styles (1,234.56 / 1.234,56); includes a PDF↔PDF comparison pair and 4 PDFs for reconciliation |
| Multi-invoice PDF | 1 | 3 invoices, one spanning two pages |
| Scanned PDF | 4 | rendered at 150 DPI, rotated, blurred |
| PNG / JPG photos | 3 / 2 | same degradation |
| TIFF / multi-page TIFF | 1 / 1 | multi-page TIFF holds 2 invoices |
| XLSX / XLS / CSV registers | 2 / 1 / 1 | title rows above the header, `;`-delimited CSV, one register for reconciliation |
| Corrupted | 5 | truncated PDF, encrypted PDF, executable renamed `.pdf`, broken `.xlsx`, corrupt PNG |

31 invoices with known values in total. The evaluator uploads every file
through `POST /documents/upload`, waits for the background jobs, reads
results from the API, and runs a PDF↔PDF comparison and a PDF↔spreadsheet
reconciliation. Processing time is measured from job creation to job
completion, with all 37 files submitted at once (so it includes queueing).

**Scoring**: a field is correct if the normalized value equals the label
(amounts as Decimal, dates ISO, text case/whitespace-insensitive).
Precision = correct / predicted, recall = correct / labelled. Header fields:
invoice number, date, supplier, customer, currency, subtotal, tax, total.

Per-field (LLM + cross-check): invoice number, date, supplier, currency,
subtotal, tax and total all **1.00** precision and recall; customer name
0.94. The two wrong customer names are OCR character errors on photos
("plc" read as "pic"). Field accuracy by kind: native PDF 100%,
multi-invoice PDF 100%, JPG 100%, TIFF 100%, multi-page TIFF 100%, scanned
PDF 96.9%, PNG 95.8%.

Mean processing time by kind (LLM, under load): spreadsheets 2.7–3.7 s,
native PDF 25.9 s (median 15.9 s), scanned PDF 21.0 s, PNG 25.6 s, JPG 32.6 s,
TIFF 30–34 s. Almost all of it is the LLM call and its queue; parsing and OCR
take 1–3 s per page batch.

### What the cross-check changed (measured on the same dataset)

The first run used the LLM alone. It showed the LLM's typical errors:
line-item amounts placed in `shipping_amount`, and lines dropped on a
two-page invoice. Adding the verified cross-check against the rule-based
extractor changed:

| | LLM alone | LLM + cross-check |
|---|---:|---:|
| Line-item totals recovered | 82.0% | 99.2% |
| False arithmetic flags | 20.7% | 3.4% |
| Mean time per document | 148.2 s (LLM concurrency 4) | 23.9 s (concurrency 8) |

The LLM still adds value over the rules alone: it found an invoice the
rules missed (the second invoice in the multi-page TIFF), and it improved
field recall from 0.968 to 1.00 on 7 of 8 fields.

## Large-document benchmark

`make benchmark` on the same stack, LLM extraction enabled
(`evaluation/results/benchmark-*.json`):

| Document | Pages | End-to-end | Invoices found | Parsing | LLM extraction | Indexing |
|---|---:|---:|---:|---:|---:|---:|
| Native PDF, 250 four-page invoices (15 MB) | 1,000 | 522 s (8.7 min) | **250/250** | 17 s | 436 s | 51 s |
| Scanned PDF, 50 invoices (OCR) | 50 | 147 s | **50/50** | 21 s | 106 s | 2 s |

* Parsing of a 1,000-page PDF takes 17 s and memory stays flat: the peak
  OCR worker was 573 MiB, because pages are processed one at a time in
  10-page tasks.
* The bottleneck is the LLM provider: 250 calls at 8 concurrent calls on
  Mistral's free tier is about 34 invoices per minute (about 49,000 per day).
  Higher provider limits or more extraction concurrency scale this linearly;
  OCR scales with `worker-ocr` replicas.

## Limitations

* The dataset is **synthetic**, generated by this repository with known
  layouts, and the rule-based extractor was developed against the same
  layout family. Real supplier invoices are more varied, so expect lower
  scores. The evaluator works with any folder of files plus a `labels.json`
  in the same format, and should be run on a labelled sample of the
  company's real documents.
* 31 invoices: one error moves a field's recall by about 3 percentage points.
* Single machine (10-core Apple Silicon laptop, Docker Desktop); timings
  include queueing for the free-tier LLM API.
